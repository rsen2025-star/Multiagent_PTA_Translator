PipeLine:
Input SOAR Agent through a load file --> Map each rule into IF (Condition)-Then (Action) Rules--> PTA Extractor (Location, Initial Location, Clock, Act & Transitions) --> Mechanically extract code

SOAR      
sp {train*propose*approach
    (state <s> ^position far ^train-count 6)
-->
    (<s> ^operator <o> + =)
    (<o> ^name approach)
}
sp {train*apply*approach
    (state <s> ^operator <o> ^position far ^train-count 6 ^io.output-link <out>)
    (<o> ^name approach)
-->
    (<s> ^position far -)
    (<s> ^position near +)
    (<s> ^train-count 6 -)
    (<s> ^train-count 0 +)
    (<out> ^signal approach)
}

Extractor
  L (locations): [far, near, in]   [var=state_position]
  l-bar (init) : far   [init rule]
  clock       : [state_train_count]   [bound=7]
  Act          : [approach, enter, exit]   [operator names]
  transitions  :   [propose + apply]
    [approach] far --(state_train_count >= 7)--> near   resets=[state_train_count] updates=[state_io_signal = approach]
    [enter] near --(state_train_count >= 7)--> in   resets=[state_train_count] updates=[]
    [exit] in --(state_train_count >= 7)--> far   resets=[state_train_count] updates=[state_io_signal = exit]


Emitter
   
module train

    state_position : [0..2] init 0;
    state_train_count : clock;

    invariant
        (state_position=0 => state_train_count<=7) &
        (state_position=1 => state_train_count<=7) &
        (state_position=2 => state_train_count<=7)
    endinvariant

    [state_io_signal_approach]   state_position=0 & state_train_count>=7   ->   (state_position'=1) & (state_train_count'=0);
        	▲         	   └───────────── guard ─────────────┘            └───────────── updates ─────────────┘
          Action/Label

    [state_io_signal_approach] state_position=0 & state_train_count >= 7 -> (state_position'=1) & (state_train_count'=0);
    [enter] state_position=1 & state_train_count >= 7 -> (state_position'=2) & (state_train_count'=0);
    [state_io_signal_exit] state_position=2 & state_train_count >= 7 -> (state_position'=0) & (state_train_count'=0);

endmodule

SOAR Basic (map to prism):
State: A state is the current problem-solving context held in working memory. (State Position)
Operator: The unit of action/decision. SOAR works on one operator at a time, and each operator is defined by rules for its lifecycle (propose, apply) pair rely on it. (Action/Label + Updates)
Conditions: The if side. (Guard)

[https://soar.eecs.umich.edu/soar_manual/01_Introduction/]

** How these positions (far, near, in) or ctrl_state or gate_positions are mapped?
1. Changes: the apply rule keep reassigning.
2. Checks: Guards keep testing it
Rule Mapping: IF Then Rules
Extractor: Use changes and checks logic
Emitter: Write Prism code by turning words into numbers.

** How the labels/action are selected? 
Rule Mapping: Records each operator's name (from ^name) and notes any I/O link it touches.
Extractor: Gathers those names into Action.
Emitter: For each move, write it into labels. [state_io_signal_approach]

** How updates are mapped?
The position: Is there any location change? (far --> near)
Clock: Did clock make updates?
Any other variable changes?
Rule Mapping: Same IF Then rules
Extractor: Check mapped rules against those three conditions and stores.
Emitter: Writes the code line.

** How clocks are mapped? 
1. The clock variable counts itself and see is it an arithmetic operation?

** I created load.soar files just to track them. 

**Assusmptions:
1. A file is a "list of agents" only if a source line points to a file named exactly load.soar and folder name = the agent name. Hardcoded path to agent.
2. Detection: a self-incrementing variable is a clock.
3. Encoding: SOAR threshold N → PRISM bound N+1, due to soar processing delays
4. There will be a dedicated soar rule for only clock.
5. I/O linked variables in soar will act as syncronization between modules (approach, exit etc.)

What we cant do from the meeting itself:
1. We can't make the PTA exactly equal to SOAR
2. We can't invent real continuous behavior (e.g SOAR can't tell us what happent between 1st & 2nd tick)
3. We can't trust 'liveness' property blindly
4. We can't detect clock perfectly
